Resumen Ejecutivo
Visión general del sistema AgentForge ULTIMATE — Fábrica de Agentes IA Autónomos
🎯 ¿Qué es AgentForge?

AgentForge ULTIMATE es una plataforma de inteligencia artificial que permite a usuarios (técnicos y no técnicos) crear, desplegar y gestionar aplicaciones web, móviles, software y automatizaciones mediante una interfaz conversacional con un "Arquitecto IA". El sistema utiliza un enjambre (swarm) de agentes especializados que generan código, lo validan, lo despliegan en contenedores Docker y gestionan automatizaciones a través de n8n.

Puntos Críticos
✅ Componentes que Funcionan
  • Autenticación email/password con JWT
  • Contexto de autenticación + persistencia localStorage
  • FastAPI server (9 routers, middleware CORS, audit, rate-limit)
  • Modelos PostgreSQL (User, Project, Task, Deployment, etc.)
  • Celery worker con asyncio loop
  • ConsultationService (interview 3-phase con fallback chain)
  • Agent Factory (plan → code → deploy pipeline)
  • Lyra optimizer (prompt optimization)
  • NeuralBrain (clasificación heurística)
  • Docker Orchestrator (build + run + health check)
  • Quality Gate (ESLint + Pylint)
  • SCA Scanner (vulnerability DB offline)
  • n8n Orchestrator (workflow creation via REST)
  • Projects CRUD, Marketplace, Security, Admin
⚠️ Componentes que Fallan
  • Google Login (useGoogleLogin flow mismatch — code vs access_token)
  • Pantalla negra del frontend (servidor no corre en puerto 3009)
  • n8n workflow NO se crea para tipos != "agent-creator"
  • n8n web admin UI/UX sin diseño profesional
  • Health check DNS container falla en Docker Desktop Windows
  • Se crean 2 contenedores por 1 proyecto (duplicación)
  • Neural Brain RL model sin entrenamiento real
  • WebContainer preview requiere HTTPS en producción
  • Sandbox test usa node:18 pero proyecto usa node:20
  • Docker build timeout 300s insuficiente para Next.js

Componentes del Sistema — Análisis Detallado
Cada componente, su responsabilidad, inputs, outputs y dependencias
📂 agent_factory.py

Core del sistema. Orquesta todo el proceso de creación.

  • Inputs: user_request, user_id, solution_type (optional)
  • Outputs: {type, data: {flow_id, editor_url, code, n8n_status, container_id, port, url}}
  • Dependencias: lyra_optimizer, neural_brain, neural_brain_rl, n8n_orchestrator, docker_orchestrator, quality_gate, sca_scanner, chromadb
  • Métodos clave: process_request(), generate_plan(), generate_code_from_plan(), apply_self_healing()
  • LLM Chain: Local AI → Groq → Gemini → OpenRouter → Heuristic
  • Agent Types: web-builder, app-builder, agent-creator, software-builder
📂 docker_orchestrator.py

Parsea código markdown, genera Dockerfiles, construye y ejecuta containers.

  • Inputs: markdown_code, agent_type
  • Outputs: {status, container_id, port, url, health_check}
  • Dependencias: Docker SDK, port_manager, sandbox_test, health_checker
  • Métodos clave: deploy_app(), parse_markdown_to_dir(), _inject_base_template(), _pre_build_syntax_check(), _run_sandbox_pre_build(), _capture_container_logs()
  • Stack Detection: Next.js, Python/FastAPI, Express/Node, static HTML (Nginx)
  • Health Check: 10 retries, exponential backoff, 3 fallback methods
📂 consultation_service.py

Servicio de entrevista conversacional con el usuario.

  • Inputs: conversation_history (list of {role, content})
  • Outputs: {status: "ASKING"|"READY", message, blueprint?, session_id}
  • Dependencias: Groq, Gemini, Anthropic, OpenRouter
  • Flujo: 3 fases: Tipo → Customización → Blueprint
  • Fallback chain: Groq → Gemini → Claude → OpenRouter
  • System prompt: Defines 3-phase interview flow strictly
📂 neural_brain.py

Clasificador de intención del usuario (qué tipo de solución necesita).

  • Inputs: request_text (string)
  • Outputs: {action, confidence, reasoning, source}
  • Dependencias: Local AI, Groq, Gemini, OpenRouter
  • Detección especial: Keywords de automatización (whatsapp, telegram, n8n, chatbot, etc.) → force agent-creator
  • Fallback chain: Local AI → Groq → Gemini → OpenRouter → Heuristic
📂 n8n_orchestrator.py

Crea workflows reales en n8n vía API REST.

  • Inputs: project_id, plan_text, name, system_prompt
  • Outputs: {flow_id, editor_url, status, message}
  • Dependencias: n8n REST API (/api/v1/workflows)

🔄 generate_agent_task

Tarea principal de Celery. Recibe el prompt del usuario y ejecuta todo el pipeline de creación de forma asíncrona.

  • Recibir parámetros
    prompt (string), user_id (string), solution_type (optional string)
  • Actualizar Task a RUNNING
    UPDATE Task SET status="RUNNING" WHERE id = task_id
  • Crear asyncio event loop
    loop = asyncio.new_event_loop() + nest_asyncio.apply() para permitir asyncio en Celery
  • Ejecutar factory.process_request()
    loop.run_until_complete(factory.process_request(prompt, user_id, solution_type))
  • Serializar resultado
    CustomJSONEncoder para Enums, dataclasses, UUIDs, datetimes
  • Guardar en DB
    UPDATE Task SET status="SUCCESS"/"FAILURE", result_data=JSON, project_id=UUID
📋 Configuración Celery: Broker y backend = Redis (redis://redis:6389/0). Serialización = JSON. Auto-discover tasks desde app.workers. Prefetch multiplier = 1 (optimizado para evitar acaparamiento de tareas).

🖥️ Pantalla Negra Post-Deploy Fallido — Causa Raíz

Cuando un deploy de automatización falla, la pantalla se queda negra porque HomeView.tsx no maneja correctamente el estado result.type === 'error'.

🔴 Problema técnico: En HomeView.tsx línea 200, isSidebarActive solo evalúa a true para 'application' o 'automation'. Cuando el deploy falla, el backend retorna {type: 'error', ...} o {status: 'error', ...}, lo que hace isSidebarActive = false. El resultado es que el layout cambia a pantalla completa sin sidebar, pero el bloque de resultados no renderiza correctamente el error porque espera result.data con una estructura que no existe.
  • Línea problemática: const isSidebarActive = result && (result.type === 'application' || result.type === 'automation');
  • Efecto cascada: Cuando result.type es 'error' → sidebar se oculta → el área principal intenta renderizar el bloque de resultados → result.data?.audit y result.data?.telemetry son undefined → se renderiza solo result.message que puede ser vacío → pantalla negra
  • Además: Si el resultado viene como {status: 'error'} en vez de {type: 'error'}, la verificación result.type es undefined y todo el renderizado se rompe
