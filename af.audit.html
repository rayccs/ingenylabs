Flujo de Creación de Proyecto

5 fases, 9+ sub-pasos en el worker, múltiples puntos de decisión y fallback. Click en cada fase para expandir.

1

Consultación Interactiva — 3 Fases

Usuario envía idea del proyecto

POST /api/v1/orchestrate/consult {message, session_id} → orchestrate.py → consult_architect() → SELECT/CREATE ChatSession → ConsultationService.generate_response()

System prompt: 3-phase flow

Type → Customization → Blueprint. El LLM debe responder JSON con {status: "ASKING"|"READY", message, blueprint?}

Cadena de fallback LLM:
Groq (llama-3.3-70b)
Gemini (gemini-2.0-flash)
Claude (claude-3-5-sonnet)
OpenRouter (gemini-2.0-flash-lite:free)
Loop ASKING hasta READY

Mientras status == "ASKING", el arquitecto hace preguntas de tipo, personalización y blueprint. El usuario responde iterativamente.

Ejemplo: "¿Qué tipo de solución necesitas? 1) Web 2) App 3) Software 4) Automatización"
status == "READY" → Blueprint generado

Respuesta: {status: "READY", blueprint: {agent_type, features, stack, detailed_prompt}} → Se muestra al usuario para aprobación.

BUG #12: LLM puede no seguir estrictamente el 3-phase flow → Blueprint sin contexto suficiente
2

Blueprint Approval

Blueprint mostrado al usuario

Se muestran: agent_type, features, stack, detailed_prompt. El usuario revisa y decide aprobar o modificar.

Click "Crear Proyecto"

POST /api/v1/orchestrate/create {prompt, name, solution_type?} → Dispara la Fase 3 (async vía Celery).

3

Creación Async — Celery Queue

INSERT Task en PostgreSQL

Task(status="PENDING", request=prompt, type="agent_generation") → generate_agent_task.apply_async(args=[prompt, user_id, solution_type]) vía Redis broker (port 6389)

Frontend inicia polling

GET /api/v1/orchestrate/status/{taskId} cada 2 segundos → Muestra "Generando agente..." + spinner

Celery Worker ejecuta task

generate_agent_task(prompt, user_id, solution_type) → UPDATE Task SET status="RUNNING" → agent_factory.process_request()

4

Worker Execution — 9 Sub-pasos

4.1 Prompt Optimization — Lyra

lyra_optimizer.optimize(prompt) → {enhanced_prompt, analysis...}

BUG #11: lyra_optimizer.py puede no estar actualizado
4.2 Agent Type Decision — NeuralBrain + RL
Si solution_type proporcionado SKIP classification, usar directamente. decision = {action: solution_type, confidence: 1.0}
Si NO solution_type (fallback) neural_brain.analyze_request(prompt):
1. Check automation keywords (whatsapp, telegram, n8n...)
Match automation → {action: "agent-creator", confidence: 0.95}
No match → Fallback: Local AI → Groq → Gemini → OpenRouter → Heuristic
+ neural_brain_rl.decide_agent_type(): VAE encode → GRU → SAC select_action
BUG #8: Keyword matching limitado (no cubre "cotización", "inventario", "descuento")
BUG #20: Modelo RL no entrenado con datos reales → decisiones aleatorias
4.3 Plan Generation
action == "agent-creator"
LLM genera Plan JSON: {description, architecture, system_prompt, model, tools[]}
→ n8n_orchestrator.create_flow_for_project():
_detect_auth_required() → _build_workflow_json() (trigger + code node + respond node)
POST /api/v1/workflows → PATCH activate → {flow_id, editor_url}
→ n8n_web_admin_generator → {index.html, server.js, package.json}
BUG #6: n8n workflow NO se crea cuando agent_type != "agent-creator"
BUG #7: HTML generado sin UI/UX usable
action == web/app/software-builder LLM genera architecture plan (texto/JSON)
4.4 Code Generation
web-builder SINGLE index.html con Tailwind CDN + GSAP + Phosphor Icons
app-builder (Python) FastAPI main.py + requirements.txt
app-builder (JS) Next.js/React code + package.json
software-builder Python/Node scripts
agent-creator code = plan_json (ya generado en 4.3)
→ apply_self_healing(code, plan): Audit → find issues → regenerate → re-audit
4.6 Quality Gate — Score mínimo: 70

run_eslint(--no-eslintrc) + run_pylint(E0602) → final_score = avg()

score >= 70 Passed
score < 70 FAILURE — Quality Gate falló
BUG #9: ESLint --no-eslintrc da falsos positivos en código generado por IA
4.7 SCA Scanner

Extraer dependencias → Check contra vulnerability DB local → SCA_BLOCK_CRITICAL

No vulnerabilidades críticas {valid: true}
Vulnerabilidades críticas FAILURE
4.8 Docker Deploy

parse_markdown_to_dir → _inject_base_template → _pre_build_syntax_check (node -c / python -m py_compile) → _run_sandbox_pre_build → docker images.build (timeout: 300s, 3 intentos)

BUG #10: Timeout 300s puede ser insuficiente para Next.js builds
BUG #13: Sandbox usa node:18-alpine vs node:20 del proyecto
Si build success → port_manager._get_free_port() (8000-9000) → containers.run
Health Check Loop — 10 retries, exponential backoff:
Backoff: 5s → 10s → 15s → 20s → 30s | Fallbacks: docker exec curl → log analysis (listening/ready/started)
BUG #4: http://{container_name}:3000 puede fallar por DNS en Docker Desktop Windows
BUG #5: Se crean 2 contenedores para 1 proyecto (web-builder + n8n admin)
Health check FAILED Captura logs (tail=200) → Guarda en /tmp/agentforge-ctn-{id}-failed.log → NO elimina container (debug)
4.9 Persist Results
Deploy SUCCESS INSERT Project + INSERT Deployment + UPDATE Task status="SUCCESS", result_data={project_id, container_id, port, url}
Deploy FAILED INSERT Project (still saved) + UPDATE Task status="FAILURE", result_data={error}
